Brand-new-user creation from the checkout email is unchanged (no account to hijack yet — pre-existing, tracked for the email-verification hardening follow-up). "Checkout with password first, then Google" links via Better Auth's default implicit account linking (Google returns a verified email, the seeded row is `emailVerified: true`) — no `trustedProviders` config. `apps/web` has `error.tsx` / `global-error.tsx` / `not-found.tsx`; `signIn.social` passes `errorCallbackURL: /login?error=oauth`.
- **Hosted checkout identity + dedup (WHO-285):** `POST /api/billing/checkout` reads `c.get("userId")` — the marketing pricing form POSTs cross-subdomain but the `app.domi-ops.com` session cookie still rides along (same-site under the shared `domi-ops.com` registrable domain). A signed-in caller who **already has a household** is redirected to `/dashboard` (no session created). Otherwise it stamps `client_reference_id` = userId (+ `subscription_data.metadata.whomeUserId`) on the Checkout Session; no `customer` is passed, so each checkout gets its own Stripe customer (one subscription per customer keeps the webhook lifecycle handlers, which filter by `stripeCustomerId`, unambiguous). The `checkout.session.completed` webhook validates `client_reference_id` against `users`, attaches that user as owner directly (they skip the `/setup` wizard), and `resolveOrProvisionHousehold` reuses a household only by exact Stripe customer or by the `client_reference_id` user's existing membership — **never by a Checkout-typed email** (payer-controlled, could point at another tenant). `hosted-setup/complete` and `hosted-setup/validate` only act on / disclose a session when `session.client_reference_id === c.get("userId")` (session ids leak via the `/setup` URL); an anonymous session still uses the email path with the existing `signin_required` guard. Before this, one person checking out twice (or once per device, or with a different email than their login) got N Stripe customers + N households + a forked account. Follow-ups tracked on WHO-285: persist `customer_email` on `household_subscriptions` for a safe email-based dedup; enforce one checkout/subscription per user (a fast double-submit can still leave an orphan trial); "resume checkout" detection on `/pricing?checkout=finish`.

### Goals module

- API: `/api/goals` (`goals.ts`, `requireHouseholdModule(..., "goals")`) — goals CRUD, **`PATCH
  .../milestones`** (full ordered-array replace of not-yet-achieved milestones; achieved
  milestones are immutable — server enforces ascending thresholds), **`POST .../progress`** /
  **`DELETE .../progress/:eventId`** (manual amount+note log/undo), **`POST
  .../milestones/:id/claim`**, **`GET/PATCH /redemptions`** (owner/admin approve|deny), **`GET/
  POST/PATCH/DELETE /rewards`** (owner/admin catalog write; archive instead of delete once a
  reward has redemption history), `GET /glance`.
- **Model:** a goal has ordered milestones (threshold/title/optional reward) — the last milestone
  is the goal's completion, no separate target field. `goal_progress_events.sourceType` is an
  enum already covering `chores`/`health`/`school` for WHO-323/324/325, plus a reserved
  `sourceEventType` text column for the health phase — only `manual` is wired up this phase.
  Milestone `achievedAt` / goal `completedAt` are a ratchet (never unset by a later correction).
  Progress is recomputed live from `goal_progress_events` by `recomputeGoalProgress` on every
  read/write — no denormalized running total, no hooks into chores/health/school's write paths.
- **Visibility:** reuses `note_visibility` (`household`/`private`) — unlike health, **owner/admin
  do get an override** on private goals (they must be able to see/approve a kid's private goal).
- DB: migration `0073_goals_rewards` — `goals`, `goal_milestones` (unique `(goal_id,
  sort_order)`), `goal_progress_events`, `goal_rewards`, `goal_reward_redemptions` (unique
  `milestone_id` — one claim per milestone).
- UI: `/goals` — Goals / Rewards / Approvals tabs (`GoalsPageClient.tsx`, same tab-bar pattern as
  Health); milestone editor is an in-memory ordered array (`goals/MilestoneListEditor.tsx`,
  modeled on `MedTimesEditor`) submitted as one array, not per-row API calls. Dashboard glance
  tile (`buildGoalsTile` in `TodayGlance.tsx`).
- **Not built this phase:** pooled/multi-contributor goals, push notification on milestone-cross
  or redemption-decided, points/karma integration, chores/health/school auto-progress (WHO-323/
  324/325) — natural follow-ups, not started.
