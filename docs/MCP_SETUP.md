# Assistant connections: hosted and self-hosted setup

WHO-478 preparation, 2026-10-23. Private synthetic acceptance exists for the
surfaces below. A real-household pilot and public rollout are still pending.
Standard MCP and the shared briefing skill are included in the hosted base price
and free for self-hosting. Bring your own assistant account; Domi Ops supplies
neither model credits nor an unlimited inference service.

## What a connection shares

An approved connection can read persisted shopping items, chores and notes the
member explicitly selects. Notes start empty. Current membership, record access,
module availability and consent are checked for every read. Recurring chores are
not generated by a briefing. Calendar, School, Health, Google-derived records,
attachments and changes to household records are outside this integration.
See the exact [fields and omissions](MCP_READ_TOOLS.md).

Connecting transfers the permitted results to the chosen assistant provider.
Review its account settings and retention terms before consenting. Domi Ops
records your attestation; it cannot inspect or enforce a provider's privacy
switches. Disconnect stops future access and does not delete copies in an
assistant conversation. Installation alone grants no household access.

## Operator prerequisites

Complete these before inviting anyone to connect:

1. Pin a reviewed build. Require green authorization/isolation CI for both
   `single` and restricted-role two-household `shared` modes, plus the normal
   release checks. Client tests alone do not replace that matrix. Record the SHA
   and results in the [pilot record](templates/MCP_PILOT_RECORD.md).
2. Follow the applicable [self-host setup](SETUP.md),
   [hosted operations](../deploy/HOSTED_OPS.md) and
   [release process](RELEASE_PROCESS.md). Back up first; apply migrations through
   `0103_mcp_authorization` and `0104_mcp_gateway` in order and rerun the application
   role installer. The running application uses its restricted role, never the
   migration/admin connection. See [authorization](MCP_AUTHORIZATION.md).
3. Obtain authorization for the exact deployment change. A PR, test pass or this
   checklist does not authorize deployment, public plugin publication or a tag.
4. Preserve the existing `SESSION_SECRET` and `ENCRYPTION_KEY` in the deployment's
   private secret store. Do not print Compose environment output, session cookies,
   authorization URLs, API keys or client secrets into support tickets. Never put
   secrets in a skill ZIP or manifest. An assistant's model API key is not a Domi
   Ops MCP credential.
5. Use a stable canonical HTTPS `PUBLIC_APP_URL`, without path/query/fragment.
   Keep `MCP_SYNTHETIC_DEPLOYMENT=false` on every real-data deployment. Only after
   the gates pass, enable `MCP_ENABLED` in the actual API/web/worker environment
   and apply the change through that deployment's documented restart procedure.

Hosted operators own TLS, routing, migrations and client provisioning; customers
do not receive a database URL or install an auth broker. Self-host operators own
those same prerequisites on their own infrastructure. The implementation and
consent rules are identical. Hosted subscriptions in read-only state still permit
entitled reads; disabled modules and record permissions still restrict access.
No new integration SKU is required.

### HTTPS and discovery

`MCP_READ_SCOPES` optionally limits this deployment's reads. For a shopping/chore
pilot, set `MCP_READ_SCOPES=shopping:read,chores:read` consistently on its services.
Both resource and issuer discovery advertise that subset plus `offline_access`;
registration, consent, token refresh and live access enforce it. Omitting the
setting retains all three reads. Empty, duplicate or unknown values fail startup.
Changing it requires an application restart. Disabled scopes are refused for
existing tokens too; this does not widen or reactivate a grant.

This is deployment-wide, including on hosted services. Review all affected
connections before narrowing it; it is not a per-household setting. Individual
consent and note selection still restrict each grant. Gemini requests every
advertised scope in the observed flow, so align the deployment's advertised reads
with the reviewed client profile before creating its connector. Do not add note
permission to bypass a shopping/chore-only pilot's scope mismatch.

Route the exact [gateway/discovery/provider paths](MCP_GATEWAY.md#enablement-and-routing)
through the supported Caddy or Next bridge, preserving public Host and bearer
Authorization. Issuer is `PUBLIC_APP_URL/auth`; resource is
`PUBLIC_APP_URL/api/mcp`. Do not derive either from arbitrary forwarded headers.
Cloud connectors must reach the app and OAuth endpoints over valid HTTPS; a LAN
URL is insufficient for Claude. The private OpenAI tunnel is a separate ChatGPT
route, not a general cloud-provider tunnel.

Expose only the intended app ingress. Do not expose Postgres, Redis, object-store
administration or fixture guides. Do not disable TLS verification, auth, RLS or
consent to resolve discovery failures. HTTP loopback is a development/test
exception. Temporary synthetic tunnel instructions are not production hosting.

Check unauthenticated resource and authorization metadata against the canonical
origin, then check that an unauthenticated MCP POST is refused with its OAuth
challenge. GET/HEAD 405 is expected and is not proof that OAuth failed. Correlate
status, timestamp and metadata-only request IDs before repeating a linking flow.

### Approved client provisioning

Provision a separate reviewed client per provider and deployment through the
trusted server-side `createBetterAuth(...).mcp.registerClient` entry point with
an authenticated session. It is not an ordinary HTTP administration endpoint.
Anonymous registration, machine grants and auto-consent remain disabled.
Claude can instead use the exact published-identity path when the operator sets
`MCP_CLAUDE_ENABLED=true`; see [Claude onboarding](MCP_CLAUDE.md). This avoids
manual registration and session extraction on both hosted and self-host servers.
ChatGPT has its own default-off `MCP_CHATGPT_ENABLED` published-identity path;
see [ChatGPT onboarding](MCP_CHATGPT.md). Its managed signing keys are fetched
only from OpenAI's exact approved URL. No customer API key or client secret is
needed; each member still signs in and reviews the provider disclosure.
Other metadata identities remain unapproved. The operator CLI below remains for
manually approved clients and older evaluations.

The operator must supply the exact observed provider callback, public PKCE S256
configuration (or a separately reviewed confidential-client configuration), the
exact resource, the approved scopes and a versioned provider profile. Real-data
profiles use `dataMode: "household"`; profiles default disabled. Request
`offline_access` explicitly when refresh is needed; it grants no domain reads.
Do not guess a callback from another account or reuse a synthetic client ID.

Use the local [operator provisioning procedure](MCP_PROVISIONING.md), which
previews without DB access and requires confirmation before creating a public
ChatGPT/Claude/Gemini household profile. Existing `scripts/mcp-chatgpt/register-client.mjs`,
`scripts/mcp-claude/register-client.mjs` and Gemini's helper remain guarded QA tools.
Do not remove those guards, copy fixture credentials, insert provider/grant rows
manually or expose registration over HTTP. Local synthetic verification is not
evidence that a real target has been provisioned or authorized for deployment.

2026-10-23 privacy recheck: Google's custom-app instructions still require Keep
Activity, and its privacy notice covers training and human review. The owner
approved retaining Gemini as an informed opt-in instead of banning the provider.
This changes policy, not deployment or individual member consent. See [custom-app requirements](https://support.google.com/gemini/answer/17209137)
and [privacy notice](https://support.google.com/gemini/answer/13594961?hl=en).

Consent policy is now `2026-10-23.v3`. On upgrade, prior-policy MCP grants fail
live checks and require fresh consent to the expanded disclosure. This affects
assistant connections, not ordinary sessions or existing Google grants. No data
scope is automatically added and no schema migration is needed.

## Member setup

1. The owner/admin enables the household at `/settings/ai-connections` after
   discussing the sharing boundary with participating adults. Each eligible
   adult grants their own connection; owner approval does not consent for others.
2. Use the provider guide above to add the approved MCP endpoint/client and
   optionally install the unchanged shared briefing skill. A skill and a live
   connection are separate requirements. Do not upload household records as setup
   material. Recheck provider privacy settings before continuing.
3. Start Connect from the assistant, sign in to Domi Ops and verify the displayed
   provider profile, household, member and exact scopes. Leave notes empty at
   first, or explicitly choose a minimal reviewed native note. Never select
   copied Google, child, health or other excluded content for the pilot.
4. Read the disclosure and affirm the adult/privacy checkboxes yourself. They
   start unchecked. Deny if anything differs from the intended connection.
   Expired or uncertain linking sessions should be restarted from the assistant;
   do not replay a saved authorization URL or repeatedly approve stale dialogs.
5. Explicitly select the installed briefing and connection where required by the
   tested surface. Request a context-first read-only briefing. Check the actual
   tool results, household-local date, record links and missing coverage. A model
   saying it connected is insufficient evidence. Unavailable data must remain
   unavailable; never substitute guessed records.
6. Review the connection in Domi Ops. Reduce scopes or note selection there when
   needed; widening access requires fresh consent. Removing refresh access
   disconnects the grant. Verify the next real request cannot obtain removed data.

## Disconnect, disable and rollback

- **One connection:** use Disconnect in Domi Ops AI Connections, then make a fresh
  request from that assistant and verify denial/no new data. Record provider
  cleanup separately if the UI reports it incomplete. Remove the remote
  connector/skill separately if desired; removal there is not proof of Domi Ops
  grant revocation. A fresh before/after test must begin with working access.
- **Whole household:** an owner/admin switches off household access. This revokes
  its grants; re-enabling requires new consent. Check that ordinary app sessions
  and existing Google connections still work.
- **Deployment stop:** set `MCP_ENABLED=false` through the deployment procedure,
  reload all relevant app instances and verify the gateway and protected-resource
  paths return 404 while ordinary app routes still work. This is a feature stop,
  not permanent grant revocation. Revoke household grants first if access must
  stay revoked after the flag is enabled again. In an incident, stop ingress
  immediately and complete revocation through reviewed recovery controls.

Preserve signing/encryption keys, ordinary sessions, Google grants, audit evidence
and additive schema. Do not delete OAuth tables or restore an old database merely
to turn off MCP. Binary/schema recovery follows [rollback](ROLLBACK.md) or hosted
operations; migrations are forward-only and a database restore can lose later
household changes. Verify the affected target after any authorized rollback.
